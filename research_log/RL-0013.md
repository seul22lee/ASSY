# RL-0013 — Ranking measured how well a family was described, not how good it is

*Date:* 2026-07-28
*Trigger:* RL-0012 recorded a correct change reverted because it flipped candidate
selection. That revert was the symptom; this entry is the cause.

*Supersedes:* RL-0012 "What was tried and rejected". The driven-side engagement
element is now in. It was never the problem.

## Why

Adding one element to `intermittent_indexing_pair` — the pin through which it
physically drives, which its own declared `CONTACT_PAIR` had nowhere to occur
without — made it lose to `pawl_advance_pair`. Three independent defects had to
line up for that, and each was doing damage on its own.

### 1. A tiebreaker inside a weighted sum is not a tiebreaker

`_score` returned `-0.6·unassigned - 0.02·part_count + 1.0·holds + 0.8·reversible
+ 0.25·(4-priority)`, commented as "element count is only a tiebreaker, so a
candidate is never preferred merely for having fewer pieces." The comment was
false. In a sum, every term trades against every other: 50 elements outweigh a
satisfied holding requirement. There are no tiebreakers in a weighted sum, only
weights.

Ranking is now lexicographic over an ordered criteria tuple. Element count applies
only where everything above is exactly equal, which is what the word means. The
five magic constants are gone, and there is nothing left to tune.

Ordering the criteria also exposed that requirement priority never discriminated
at all: `min(r.priority for r in spec.requirements)` does not mention the family,
so it added the same constant to every candidate. It had been inflating scores and
ranking nothing.

### 2. The selection was a coin flip presented as a decision

With the sum removed, BM-101's two candidates scored *exactly* equal — same
unassigned functions, same part count, both holding, neither reversible. The winner
had been decided by `max()` over catalogue declaration order. Adding one element
did not lose an argument; there had never been an argument.

This is the failure this project has now corrected in four separate places:
declaration order emitting an engineering fact. A tie is not a scoring problem to
be weighted away — it means the criteria do not separate these mechanisms, and
saying otherwise is L1, an assertion wearing a derivation's label.

`undecided_between` now records it, and Stage 02 names the typed properties the
tied candidates actually differ on. That output is the useful one: it says what a
requirement would have to state for the choice to become derivable.

### 3. Holding was a prose string tested with `bool()`

The tie was partly an artifact. `bool(fam.holding_principle)` counted
`"none inherent; tension is lost when input is released"` as a holding mechanism,
because the sentence documenting the absence is itself non-empty. Two families were
claiming a capability they explicitly disclaim, in the same field, in words.

It also cannot carry a direction, and holding is directional: the Geneva's driver
geometry locks the output both ways, the pawl blocks reverse only. Both facts were
sitting in the prose, machine-invisible — exactly what the first Stage 02 review
demanded be fixed and this field had quietly kept doing.

Now typed as `HoldingCapability{NONE, SINGLE_DIRECTION, BIDIRECTIONAL}`. This
independently corrects BM-002: `toothed_linear_drive` and `flexible_tension_drive`
no longer pose as holding mechanisms, which is RL-0004's concern removed at its
root rather than compensated for.

### 4. Element count measured description granularity

The deepest one. `part_count = len(roles)` counts *how finely the family has been
written down*. Saying that two turning bodies drive each other through a pin — a
statement about where contact physically occurs, not about added complexity — made
the family score worse. The metric punished describing a mechanism accurately, so
the catalogue was under pressure to stay vague.

Ranking now uses `body_count`: independent rigid bodies. A feature is a region of a
body and a joint is a consequence of two bodies meeting, so neither can be created
or destroyed by describing the same mechanism more carefully. The count is invariant
to granularity, which is the property a size metric has to have.

## Consequence

BM-101 is no longer undecided, and it resolved on engineering rather than on
arithmetic: 4 bodies against 5. The ratchet needs a *separate holding pawl* to do
what the indexing pair's own driver geometry already does, and once the measure was
bodies instead of declarations, that showed up as the real difference it is.

The driven-side engagement element went back in and changed no selection (8 parts
against 7, but 4 bodies against 5). With it, the output's angular state is finally
observable: the station datum moves through `(0.05,0.00) → (0.05,0.03) → (0.03,0.05)`,
and the three states are distinguishable in the drawing for the first time.

## What was deliberately not done

Nothing was weighted, ordered or thresholded to make a particular candidate win.
The direction of holding is still not used in ranking, because no requirement field
states which direction a held state must resist — that gap is now reported as a
contract advisory instead of being guessed at. Had the tie survived, the correct
output was the tie.
