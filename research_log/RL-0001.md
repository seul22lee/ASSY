# RL-0001 — Stage 01 → Stage 02 strict-consumer migration

**Date:** 2026-07-27
**Contract touched:** `BehaviourSpec`, `Stage01ContractDeficiency`, Stage 02 entry point

## Summary

Stage 02 was rewritten to consume only structured Stage 01 fields. It no longer
reads `source_text`, pattern-matches requirement prose, or infers a mechanism
from a word. Where the structured contract is insufficient it returns a typed
`Stage01ContractDeficiency` and the pipeline stops, rather than falling back to
re-reading the request.

## Trigger

A contract contradiction, not a test failure. `STAGE_01.md §5` forbids downstream
re-interpretation of the request, yet `s02_mechanical.py:53` read
`spec.source_text` to decide what the product had to do. One of the two had to be
wrong.

## Evidence

- Six general probes were run to ask whether the input quantity of a behaviour
  was recoverable from Stage 01's *structured* output alone. It was recoverable
  in **2 of 6**. The remaining four were recoverable only from prose, which is
  exactly the coupling §5 forbids.
- After the rewrite, blanking `source_text` was shown to leave Stage 02's
  fingerprint — selected id, candidate ids, functional chains, traceability,
  advisories — **bit-identical for BM-001, BM-002 and BM-101**. The same held
  under a misleading decoy text and under scrambled requirement statements.

## Root cause

`RD-2` had always required actor / action / object / condition, but the schema
gave it no representation. With nowhere structured to live, it degraded into the
free-text `statement` field. The consumer then had no honest way to learn what
transformation a requirement demanded except to re-read the request. The defect
was **absent representation**, not a careless consumer.

## Design decision

Add `BehaviourSpec` carrying `input_kind`, `output_kind`, `continuity`,
`reversible`, and select mechanism families on the resulting transformation
*signature*.

Rejected: keeping a prose fallback "for robustness". A silent fallback hides the
deficiency and rebuilds precisely the coupling being removed, so absence of
information had to become a visible, typed outcome.

Blocking policy was narrowed once during the work. The first rule blocked when
*any* behavioural requirement lacked a `BehaviourSpec`, which stopped BM-001 and
BM-002 for a gap costing no geometric information — a performance requirement
that merely *quantifies* another behaviour has no transformation of its own.
Blocking is now reserved for the case where **no** requirement anywhere declares
a usable transformation; everything else is a non-blocking advisory carried
forward.

## Stage ownership

| Field | Owner | Why |
|---|---|---|
| `BehaviourSpec` | Stage 01 | it is the interpretation of what the user asked for |
| `DeficiencyItem` / `Stage01ContractDeficiency` | Stage 02 | only the consumer knows what it needed and did not get |
| mechanism catalogue | knowledge base | Stage 02 asks the question; the knowledge base answers it |

## Generalization

Selection is keyed on `(input_kind, output_kind, continuity)`. No family is
reachable by name, and the catalogue deliberately contains **no `geneva` entry**,
so a benchmark titled "Geneva Indexing Box" cannot select a mechanism from its own
filename. A structural test asserts Stage 02's source contains no `source_text`,
no `re.*`, and none of `lift/raise/index/latch/lid/crank/geneva/rack`.

## Validation performed

- Source-text invariance across all three benchmarks, under four mutations.
- Geometry handoff audit per benchmark: golden statement → Stage 01 record →
  Stage 02 usage → geometry consequence → verdict. All pass.
- Test suite migrated off the deterministic placeholder: **71 deterministic tests
  pass**, plus 5 live-model regressions kept separate and skipped by default.
- The placeholder was **not** upgraded with fabricated `BehaviourSpec` values. It
  was renamed `IncompleteRequirementProducer` and documented as a deliberately
  invalid producer; a test asserts it emits zero behaviours and that a pipeline
  driven by it stops at Stage 02 with a typed deficiency.

## Freeze status

**Stage 01 frozen** against the geometry-relevant completion criterion: all BM
information that materially constrains later shape, motion, arrangement,
interaction or packaging is represented and actively used without source-text
reinterpretation.

## Remaining issues

- `QuantityKind` carries both `TRANSLATION` and `DISPLACEMENT` with no stated
  distinction. On a live-model run the reasoner chose
  `rotation→displacement/intermittent` for BM-101 where the catalogue holds
  `rotation→rotation/intermittent`, and Stage 02 correctly refused. This is a
  SCHEMA-category defect; it was **not** patched by aliasing the enums, which
  would have hidden it.
- Two defects were found and fixed en route that were not the subject of this
  work: Stage 05 crashed on every run reading a renamed catalogue field, and
  BM-001 reported `pass` with zero simulation evidence because the evidence gate's
  role vocabulary had drifted. The second is the L1 failure mode this project
  exists to prevent and is recorded here because it was found by contract work,
  not by a physics test.

## Next validation target

Whether Stage 02's output is *complete enough* for downstream geometry, judged
against the golden Stage 02 sections rather than against its own schema.
